# 升级部署 - 子节点 - 镜像导入

本文档用于 Sub2API 分布式子节点升级。适用于子节点机器资源较低、不适合在远端源码构建 Docker 镜像的场景。

核心原则：

- 镜像在本地、CI 或专用构建机完成构建。
- 子节点只接收镜像包，执行 `docker load` 后切换 `sub2api` 服务。
- 子节点不启动本地 PostgreSQL/Redis，继续通过 `docker-compose.remote-db.yml` 连接核心节点数据库和 Redis。
- 子节点的 `.env` 必须保留远端现有配置，不要用本地 `.env` 覆盖。
- `NODE_ID` 是运行时配置，不应写死到镜像中。

## 适用场景

- 子节点只部署应用容器，数据库和 Redis 在核心节点。
- 子节点公网带宽可接受上传一个几十 MB 到数百 MB 的镜像包。
- 子节点 CPU/内存较小，源码构建会导致 SSH 卡顿、健康检查超时或 OOM。
- 需要多节点使用完全一致的应用镜像，降低部署差异。

## 变量约定

以下变量按实际版本替换：

```bash
VERSION=0.1.144
COMMIT=68182a70
TS=20260531-102006
IMAGE="sub2api-subnode:v${VERSION}-custom-${COMMIT}-${TS}"
ARCHIVE="sub2api-subnode-v${VERSION}-custom-${COMMIT}-${TS}.tar.gz"
DEPLOY_DIR="/data/sub2api-deploy"
UPLOAD_DIR="/data/sub2api-quick-deploy"
```

建议镜像 tag 包含版本号、Git commit 和构建时间，避免覆盖旧镜像，方便回滚。

## 本地构建镜像

在当前源码目录执行：

```bash
git status --short --branch
cat backend/cmd/server/VERSION
git rev-parse --short HEAD
```

确认工作区和版本无误后构建镜像：

```bash
docker build \
  --pull=false \
  --build-arg GOPROXY=https://goproxy.cn,direct \
  --build-arg GOSUMDB=sum.golang.google.cn \
  --build-arg VERSION="${VERSION}" \
  --build-arg COMMIT="${COMMIT}" \
  -t "${IMAGE}" \
  -f Dockerfile .
```

构建完成后校验版本：

```bash
docker run --rm --entrypoint /app/sub2api "${IMAGE}" --version
```

输出应包含目标版本和 commit，例如：

```text
Sub2API 0.1.144 (commit: 68182a70, built: ...)
```

## 导出镜像包

导出为 tar：

```bash
docker save -o "${IMAGE//[:\/]/-}.tar" "${IMAGE}"
```

压缩为 `.tar.gz`：

```bash
gzip -6 "${IMAGE//[:\/]/-}.tar"
mv "${IMAGE//[:\/]/-}.tar.gz" "${ARCHIVE}"
```

如果在 Windows PowerShell 中没有 `gzip`，可以使用 Python 压缩：

```powershell
$image = "sub2api-subnode:v0.1.144-custom-68182a70-20260706-102006"
$safe = $image.Replace(':','-').Replace('/','-')
$tar = "$safe.tar"
$gz = "$tar.gz"
docker save -o $tar $image
python -c "import gzip, shutil, sys; src=sys.argv[1]; dst=sys.argv[2]; f_in=open(src,'rb'); f_out=gzip.open(dst,'wb',compresslevel=6); shutil.copyfileobj(f_in,f_out); f_out.close(); f_in.close()" $tar $gz
Remove-Item -Force $tar
```

生成 SHA256：

```bash
sha256sum "${ARCHIVE}"
```

Windows PowerShell：

```powershell
Get-FileHash $ARCHIVE -Algorithm SHA256
```

## 上传到子节点

上传到子节点 quick deploy 目录：

```bash
scp "${ARCHIVE}" root@<subnode-public-ip>:"${UPLOAD_DIR}/${ARCHIVE}"
```

远端校验 SHA256：

```bash
ssh root@<subnode-public-ip> "sha256sum '${UPLOAD_DIR}/${ARCHIVE}'"
```

必须确认远端 SHA256 与本地一致后再切换容器。

## 远端加载镜像

登录子节点：

```bash
ssh root@<subnode-public-ip>
```

确认旧容器健康：

```bash
docker inspect sub2api --format '{{.Config.Image}} {{.State.Status}} {{if .State.Health}}{{.State.Health.Status}}{{else}}no-health{{end}}'
curl -fsS --max-time 5 http://127.0.0.1:8080/health
```

加载新镜像：

```bash
docker load -i "${UPLOAD_DIR}/${ARCHIVE}"
docker image inspect "${IMAGE}" --format '{{.Id}} {{.Size}} {{.Created}}'
```

## 设置 NODE_ID

`NODE_ID` 必须是远端运行时配置，不能在本地构建镜像时写入。

如果远端 `.env` 已有非空 `NODE_ID`，不要覆盖。只有不存在或为空时，才按子节点公网 IP 写入：

```bash
ENV_FILE="${DEPLOY_DIR}/.env"
PUBLIC_NODE_ID="ip-<subnode-public-ip>"

touch "${ENV_FILE}"
chmod 600 "${ENV_FILE}" || true

if grep -q '^NODE_ID=' "${ENV_FILE}"; then
  CURRENT_NODE_ID="$(grep '^NODE_ID=' "${ENV_FILE}" | tail -n1 | cut -d= -f2- | tr -d '\r' || true)"
  if [ -z "${CURRENT_NODE_ID}" ]; then
    sed -i "s|^NODE_ID=.*|NODE_ID=${PUBLIC_NODE_ID}|" "${ENV_FILE}"
  fi
else
  printf '\nNODE_ID=%s\n' "${PUBLIC_NODE_ID}" >> "${ENV_FILE}"
fi
```

如果多个子节点共用同一个公网出口或 NAT，不能只用公网 IP 作为 `NODE_ID`，应手动设置唯一值，例如：

```bash
NODE_ID=ip-203.0.113.10-node-01
NODE_ID=ip-203.0.113.10-node-02
```

## 切换子节点镜像

先备份当前 override：

```bash
cp -f "${DEPLOY_DIR}/docker-compose.release.override.yml" \
  "${DEPLOY_DIR}/docker-compose.release.override.yml.bak-$(date +%Y%m%d-%H%M%S)" 2>/dev/null || true
```

写入新镜像 override：

```bash
cat > "${DEPLOY_DIR}/docker-compose.release.override.yml" <<YAML
services:
  sub2api:
    image: ${IMAGE}
YAML
```

检查 compose 配置：

```bash
docker compose \
  --project-directory "${DEPLOY_DIR}" \
  -f "${DEPLOY_DIR}/docker-compose.yml" \
  -f "${DEPLOY_DIR}/docker-compose.release.override.yml" \
  -f "${DEPLOY_DIR}/docker-compose.remote-db.yml" \
  config -q
```

只重建 `sub2api` 服务：

```bash
docker compose \
  --project-directory "${DEPLOY_DIR}" \
  -f "${DEPLOY_DIR}/docker-compose.yml" \
  -f "${DEPLOY_DIR}/docker-compose.release.override.yml" \
  -f "${DEPLOY_DIR}/docker-compose.remote-db.yml" \
  up -d --no-deps --force-recreate sub2api
```

注意：

- 必须带 `docker-compose.remote-db.yml`，确保使用核心节点数据库/Redis 配置。
- 必须指定 `sub2api` 服务。
- 必须带 `--no-deps`，避免启动本地 PostgreSQL/Redis 等依赖服务。
- 不要在子节点执行无服务名的 `docker compose up -d`。

v0.1.144 自定义高峰倍率迁移注意：
- 新 `sub2api` 应用容器启动时必须正常完成应用内 migration，包括 `159_add_group_peak_rate_windows.sql`。
- 这仍然只是替换应用容器，不需要重建或重启子节点本地 PostgreSQL/Redis 容器，也不要动数据卷。
- 如果回滚到旧应用容器，旧版本会忽略多时段 `peak_rate_windows`，但仍会按 legacy 第一段 `peak_start` / `peak_end` / `peak_rate_multiplier` 工作。
- 多窗口回退会退化为第一段生效；如果回退期间编辑了高峰配置，再升级时新容器读路径会优先使用 legacy 第一段以保持兼容；只有在新版本再次保存分组后，`peak_rate_windows` 才会被持久同步。

## 健康检查

等待健康状态：

```bash
for i in $(seq 1 36); do
  STATE="$(docker inspect sub2api --format '{{.State.Status}} {{if .State.Health}}{{.State.Health.Status}}{{else}}no-health{{end}}' 2>/dev/null || true)"
  if curl -fsS --max-time 5 http://127.0.0.1:8080/health; then
    echo "health ok: ${STATE}"
    break
  fi
  echo "waiting health: ${STATE}"
  sleep 5
done
```

最终确认：

```bash
docker ps --filter name=sub2api --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
docker inspect sub2api --format '{{.Config.Image}} {{.State.Status}} {{if .State.Health}}{{.State.Health.Status}}{{else}}no-health{{end}} {{.State.StartedAt}}'
docker exec sub2api /app/sub2api --version
curl -fsS --max-time 5 http://127.0.0.1:8080/health
```

确认 compose 只显示 `sub2api` 应用服务：

```bash
docker compose \
  --project-directory "${DEPLOY_DIR}" \
  -f "${DEPLOY_DIR}/docker-compose.yml" \
  -f "${DEPLOY_DIR}/docker-compose.release.override.yml" \
  -f "${DEPLOY_DIR}/docker-compose.remote-db.yml" \
  ps
```

## 回滚

如果新容器健康检查失败，写回旧镜像并重建 `sub2api`：

```bash
OLD_IMAGE="sub2api-subnode:<old-tag>"

cat > "${DEPLOY_DIR}/docker-compose.release.override.yml" <<YAML
services:
  sub2api:
    image: ${OLD_IMAGE}
YAML

docker compose \
  --project-directory "${DEPLOY_DIR}" \
  -f "${DEPLOY_DIR}/docker-compose.yml" \
  -f "${DEPLOY_DIR}/docker-compose.release.override.yml" \
  -f "${DEPLOY_DIR}/docker-compose.remote-db.yml" \
  up -d --no-deps --force-recreate sub2api
```

回滚后再次确认：

```bash
docker ps --filter name=sub2api --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
curl -fsS --max-time 5 http://127.0.0.1:8080/health
```

## 常见问题

### 本地构建会不会把本地 IP 写入镜像？

不会。当前 `NODE_ID` 是运行时配置，解析顺序为：

```text
NODE_ID 环境变量 -> 运行环境网卡公网 IP -> hostname -> 随机 fallback
```

只要 Dockerfile 不写死 `ENV NODE_ID=...`，本地构建镜像不会把本地机器 IP 带到云上。

### 为什么仍建议在远端 `.env` 写 NODE_ID？

部分云服务器的公网 IP/EIP 不会出现在容器网卡里，容器只能看到内网 IP。此时自动解析可能退化到 hostname。为了让代理测速、sticky proxy 和 managed mihomo runtime 的节点本地化语义稳定，建议部署脚本在远端首次部署时写入唯一且稳定的 `NODE_ID`。

### 子节点需要数据库镜像吗？

不需要。子节点只运行 `sub2api` 应用容器，通过 `docker-compose.remote-db.yml` 连接核心节点 PostgreSQL/Redis。升级时使用：

```bash
up -d --no-deps --force-recreate sub2api
```

不要启动本地数据库/Redis。

### 源码构建为什么不推荐在子节点执行？

源码构建会触发前端依赖安装、前端构建、Go 模块下载、Go 编译和 Docker 多阶段构建。低配子节点容易出现 SSH banner 超时、健康检查超时、Docker 拉基础镜像失败或 OOM。镜像导入部署能把这些高负载步骤从子节点移除。
